You are tasked with building a hybrid search system for an educational resource library. The system combines algorithmic search for performance with AI-powered fallback search for accuracy. The application is a static website hosted on Netlify with serverless functions.
Context and Requirements
The resource library is a JSON file containing educational materials organized by semester, course, and resource type. Each course has multiple resource categories like chapters, question banks, lab manuals, assignments, previous year papers, tutorials, syllabi, and reference books.
The search system must handle user queries in multiple formats including abbreviations, flexible word order, partial matches, and typos. For example, a user might search for "os introduction" to find the Introduction chapter in Operating System, or "dadv qb" to find Question Bank in Data Analytics and Data Visualization course.
The system is deployed on Netlify which provides static hosting and serverless functions. There is an existing chat API that uses OpenRouter with a free tier limited to 50 queries per day. The search system should use algorithmic matching for unlimited free searches and fall back to AI search only when necessary to preserve the limited daily quota.
Architecture
The search system has two tiers. Tier One is algorithmic search that runs on the client side in the browser. This tier is fast, free, and unlimited. It uses abbreviation expansion, fuzzy string matching with Jaro-Winkler algorithm, and context-based scoring to find resources. Tier Two is AI-powered search that runs through a Netlify serverless function calling OpenRouter API. This tier is used as a fallback when algorithmic search has low confidence or returns no results.
The frontend loads the resource library JSON and builds a dynamic search index without hardcoding values. The index automatically generates abbreviations and patterns from the data structure itself, allowing the system to work with any new courses, branches, or subject areas added in the future.
Algorithmic Search Implementation
Create a client-side search engine class that performs the following operations. First, it builds an index from the resource library JSON by iterating through each semester and course. For each course name, it generates multiple abbreviation variants automatically.
Abbreviation generation should follow these rules: extract first letters of each word for the most common abbreviation, add individual words from the course name, add partial words of 2 to 4 characters from each word, create two-word combinations, add common domain shortcuts like prog for programming or sys for system, and include vowel-removed variants for additional matching flexibility.
The index should store course names mapped to their abbreviations, content items mapped to their parent courses and resource types, and type patterns for different resource categories. Type patterns should include keywords that users might use when searching for specific resource types like chapters, question banks, labs, assignments, previous year papers, tutorials, and syllabi.
Implement a Jaro-Winkler distance function for fuzzy string matching. This function should calculate character matches within a distance window, count transpositions, and apply a prefix bonus for matching characters at the beginning of strings. The distance should return a score from 0 to 1 where higher values indicate better matches.
The search function should accept a query string and a threshold parameter defaulting to 0.75. It should tokenize the query into lowercase words, then perform multi-layer matching. First, it should check for exact abbreviation matches against the course index. Second, it should apply fuzzy matching to find courses that partially match query tokens even if they are not exact abbreviations. Third, it should check if query tokens match any type patterns to filter results by resource type. Fourth, it should search for content items within matched courses to find specific chapters, assignments, or other resources. Finally, it should calculate average scores across all matches, apply boost multipliers for exact matches, and return the top 5 results sorted by score along with a confidence metric.
AI Search Implementation
Create a Netlify serverless function named ai-search that accepts POST requests. The function should read the query and resource library from the request body and send both to OpenRouter API along with a system prompt.
The system prompt should instruct the AI to find the most relevant resource from the library based on the user query. It should explain the resource library structure and specify that responses must be valid JSON only with no additional text. The prompt should include rules to only return resources that actually exist in the library, to match courses to resource types to specific content, to handle vague queries by returning the top match with lower confidence, and to never make up resources.
The system prompt should include an abbreviation dictionary mapping common abbreviations to their full course names. It should provide the response format as JSON containing matched course, matched type, matched content, semester, reasoning, confidence score, path, and alternate options if the query is ambiguous.
The function should handle CORS by responding to OPTIONS requests appropriately. It should validate that the OpenRouter API key exists in environment variables. It should set proper headers including Authorization, HTTP-Referer, and X-Title for the OpenRouter API. It should use the mistral free model to keep costs at zero while on the free tier. The function should set temperature to 0.3 for deterministic responses and max tokens to 500 for efficiency.
The function should handle errors gracefully by checking response status, parsing the JSON response, extracting the content from the API response, and returning either a success response with the parsed result or an error response with the raw content if parsing fails.
Frontend Integration
Create a search interface HTML element with an input field that accepts user queries. Attach an event listener to the input that debounces the search function to avoid excessive calls. When the user types a query of at least 2 characters, call the algorithmic search engine.
If the algorithmic search returns a confidence score greater than 0.8 and has results, display those results with a green badge indicating Quick Match. If confidence is lower and the algorithm indicates AI search is needed, and if the AI search quota has not been exceeded, call the serverless AI search function.
Track the number of AI searches used in the current day using sessionStorage. Display the current AI usage as a fraction of 50 maximum queries. If the AI quota has been reached, display a message informing the user that the quota is exhausted. If no results are found from either method, display a message suggesting different keywords.
Results should display the course name, semester number, resource type if matched, specific content items if found, and a badge indicating whether the match came from algorithmic or AI search. Include a reasoning explanation for why this resource was matched to the query. If multiple content items exist, show the top 3 items.
Environment Configuration
Create a netlify.toml configuration file that specifies the build command and the functions directory path. Add environment variables for the OpenRouter API key and the site URL. The API key should be set in Netlify environment variables in the deployment settings.
Testing Scenarios
Test the system with the following queries to verify correct functionality. Search for "os introduction" and verify it matches Operating System with Introduction chapter. Search for "dadv qb" and verify it matches Data Analytics and Data Visualization with Question Bank resource type. Search for "epj servlets" and verify it matches Enterprise Programming with Servlets chapter. Search for variations like "intro os" to verify word order independence. Search for partial matches like "servelets" with intentional typos to verify fuzzy matching. Search for new courses that might be added in future branches to verify dynamic functionality.
Code Organization
The algorithmic search engine should be a self-contained class that can be imported into the frontend. The AI search function should be in the netlify/functions directory and should be completely independent from the frontend code. The frontend integration should be a separate module that instantiates the search engine, handles user input, calls both search methods, and displays results. The system prompt should be defined as a string constant within the serverless function so it can be easily modified without redeploying.
Performance and Scalability
The algorithmic search should complete in under 50 milliseconds for typical queries. The index building should complete in under 200 milliseconds even with hundreds of courses. The AI search should complete in under 2 seconds on average, with the 50 query per day limit being respected through client-side quota tracking. The system should scale to support any number of courses, branches, or resource types by automatically generating patterns from the data without hardcoding values.
Key Implementation Details
Do not hardcode any course names, abbreviations, or resource types. All matching patterns should be automatically generated from the JSON structure. The Jaro-Winkler implementation should be optimized for performance on the client side. The system prompt should be comprehensive enough that the AI understands the exact structure of your specific resource library. The frontend should gracefully handle cases where the resource library fails to load. The serverless function should validate all inputs and handle API errors appropriately. The confidence scoring should accurately reflect the likelihood that a result is correct so that the system knows when to escalate to AI search. SessionStorage should be used to track AI quota usage across browser sessions on the same day.
